# Release v20261024.0.0 against production Rails, October 24, 2026

A rerun of the [cleaned corpus protocol](bench-public-meta-20261019.md#cleaned-corpus-rerun)
on the release build, plus the first browser page-load comparison against Rails
and a footprint record. Same snapshot, same PostgreSQL 18.6 instance, same Rails
build, same benchmark script as October 19; only the Rust build changed.

## Demo summary

- **Uncached JSON, anonymous, concurrency 16:** Rust serves 4x to 18x the Rails
  throughput: latest 2,173 vs 122 req/s, categories 845 vs 203, topic JSON
  1,051 to 1,245 vs 112 to 151. Response cache bypassed on both; zero errors in
  all 96 samples.
- **Search narrows the gap to about 2x to 3x:** common term 125 vs 65 req/s,
  selective 504 vs 172, no match 1,661 vs 691. The corpus repeats text, so the
  common term is a heavy, high-match workload.
- **Browser, content visible:** a cold visit to Latest is ready in 169 ms on
  Rust vs 753 ms on Rails; a twenty-post topic in 170 vs 859 ms. Warm visits:
  104 vs 712 ms and 104 vs 819 ms. Clicking from Latest into a topic: 108 vs
  191 ms. Anonymous, loopback, no throttling, server caches warm.
- **Memory:** one Rust process, 50 MB idle and about 210 MB under this load.
  Rails' eight Pitchfork workers plus monitor, mold and service: 5.0 GiB summed
  RSS (0.85 GiB PSS) idle, 6.3 GiB RSS (PSS rising to 3.2 GiB) under load.
- **Startup:** Rust 87 ms from exec to first 200. Rails 9.8 s to first 200 and
  17.2 s until all eight workers are ready.
- **Same answers:** latest topics, category counters, topic posts with cooked
  HTML and all three search result sets matched field for field.
- **Caveats:** one laptop runs client, servers and database; no keep-alive; anonymous
  traffic only; 20k-post synthetic corpus, not a production-capacity test.
  Rails runs without nginx. Throughput differs by architecture as much as by
  language.

### Correctness spot check

The first-pass bodies were projected as on October 19 and diffed:

- Latest: ordered topic IDs, titles, posts_count (30 topics) and user IDs (40). Match.
- Categories: ordered IDs, names, topic_count, post_count (15). Match.
- Topics 67 and 77: ID, title, posts_count, ordered post IDs, post numbers and
  cooked HTML (1 and 20 posts). Match.
- Search `Discourse`, `postgres`, no match: ordered post IDs, topic IDs and
  blurbs, topic IDs and titles (50, 39, 0 results). Match; both omit `topics`
  on no match.

This is not full serializer parity. Response sizes still differ for categories
and topic JSON, which carry fields beyond the projection; topic HTML is a
rendered page on Rust and an Ember shell with preloaded data on Rails.

## Browser page load

Medians of 20 samples, Rust / Rails. `ready` ends when the fixture's content
element is visible with text, two frames later. Transfer is encoded bytes in
the measurement window. Both clicks stayed in the same document on both
implementations. No failures and no click-target mismatches.

| Scenario | Ready ms | Ready p95 ms | FCP ms | Transfer KB | Script ms |
|---|---:|---:|---:|---:|---:|
| Latest, cold | 169 / 753 | 185 / 806 | 106 / 44 | 453 / 5,579 | 31 / 176 |
| Latest, warm | 104 / 712 | 105 / 759 | 40 / 44 | 15 / 231 | 24 / 173 |
| One-post topic, cold | 143 / 670 | 154 / 718 | 92 / 44 | 409 / 5,421 | 22 / 179 |
| One-post topic, warm | 88 / 641 | 104 / 683 | 44 / 44 | 14 / 157 | 14 / 177 |
| Twenty-post topic, cold | 170 / 859 | 186 / 919 | 108 / 46 | 423 / 5,505 | 32 / 184 |
| Twenty-post topic, warm | 104 / 819 | 136 / 897 | 28 / 44 | 19 / 231 | 23 / 181 |
| Search, cold | 184 / 719 | 256 / 832 | 104 / 44 | 463 / 5,587 | 34 / 175 |
| Search, warm | 122 / 690 | 188 / 789 | 52 / 40 | 19 / 239 | 26 / 171 |
| Latest to topic, click | 108 / 191 | 126 / 256 | - | 62 / 25 | 34 / 13 |
| Topic to latest, click | 73 / 188 | 91 / 192 | - | 15 / 39 | 26 / 3 |

Read with care:

- Rails' FCP and observed LCP (44 ms) are its splash screen, painted before the
  application boots; they are not content. Compare `ready`.
- Both servers answered these anonymous document requests from their response
  caches (median TTFB 1.5 ms Rust, 3.7 ms Rails cold), so the document request
  is not where the time goes. Rails' cost is downloading and running its
  application bundle and then fetching data; Rust's pages arrive rendered.
- Without nginx, Rails serves its precompiled assets through
  `DISCOURSE_SERVE_STATIC_ASSETS=true` (Brotli files where present) and returns
  HTML, JSON and stylesheets uncompressed; Rust compresses its own responses.
  On loopback this inflates Rails' transfer bytes far more than its timings.
- Rails was restarted with that flag for the browser run and both servers were
  warmed by a one-sample run first. Cold means a fresh browser context, not a
  cold server.

There is no earlier Rust/Rails browser comparison to set this against;
[browser-bench.md](browser-bench.md) describes the harness.

## Footprint

Both processes' RSS was read with host `ps` once a second through the whole
HTTP run; Rails is the sum over its 11 Pitchfork processes (monitor, mold,
service, eight workers). "Under load" covers the seconds when oha was driving
that target, across all endpoints and both cache modes. PSS, which splits
pages shared between forked workers, was read from `smaps_rollup` every 15
seconds. MB here means MiB.

| Measure | Rust | Rails |
|---|---:|---:|
| Idle after start, RSS | 50 MB | 5,144 MB |
| Idle after start, PSS | 48 MB | 872 MB |
| Under load, median RSS | 210 MB | 6,488 MB |
| Under load, peak RSS | 216 MB | 7,296 MB |
| After the run, RSS / PSS | 216 / 214 MB | 6,611 / 3,289 MB |
| Exec to first 200 | 87 ms (84 to 88, five runs) | 9.8 s (one run) |
| All workers ready | (one process) | 17.2 s |
| Binary size | 185 MiB (194,097,504 bytes), 161 MiB stripped | (Ruby application) |

Rust's growth from 50 to about 210 MB is most likely its per-connection statement caches and
the anonymous response cache filling. `scripts/bench-startup`, which warms with
100 requests to five pages, reported 50 MB idle and 79 to 82 MB afterwards.
The release profile has no size settings; most of the binary is embedded
assets.

Rails did not change, so its rows show the session-to-session drift on this

- **Topic HTML, about 9% slower.** All three rounds (483 to 495 req/s) fall

  with the week's topic-page work. Not profiled.
- **Selective search, 12% lower median,** but the rounds overlap (500 to 558
  now, 493 to 575 then). Treat it as noise until a longer run says otherwise.

**Follow-up: the topic HTML regression** (measured after this run; the table
above is unchanged). It was real: on the same database, alternating builds,
`ef9eec98` served 599 to 618 req/s and `85672018` 529 to 541. The page went
from 76 to 96 SQL statements per request. Seventeen of the new ones were page
chrome read from the theme tables on every page, where Rails reads its caches:
the color scheme meta tags and stylesheets (7), the theme stylesheet links (6,
including the same `theme_fields` query three times) and the theme HTML fields
(4). Branch `perf/topic-html-regression` keeps those per site until the theme
tables change, checked with the fingerprint query the SVG sprite already ran
on each page. The page now runs 79 statements and the markup is unchanged.
Four alternating rounds each: `85672018` 529 to 540 req/s, the fix 568 to 580,
`ef9eec98` 599 to 604. Most of the remaining gap is the three statements the
week's correct output added (the paged post id lookup Rails also does, the
small logo for the header topic info, the category's `read_restricted` for the
quote button) and the larger page.

The no-match search's third round was again the outlier (1,038 req/s, against
1,014 on October 19, with the other rounds near 1,670); it repeats at the same
position in the run and is excluded by the median.

Between the two builds: 273 commits and 107 merged branches, about 62,000
lines added under `src`, `static` and `templates`. Among them: infinite loading
on discovery lists, the topic view's post-number entry and URL tracking, staff
topic views (deleted posts and topics, ignored users), moderator scope for the
review queue and reviewable counts, the review pages and queued posts, visit
tracking and incoming links on topic loads, theme SCSS/HTML fields, color

footprint table. October 9's historical process figures (Rust 75 ms and 32 MB

## Caveats

As [BENCH.md](../BENCH.md#reading-the-results) frames them:

- Compare rows within this run. The October 19 comparison above holds only
  because the Rails control stayed within its usual drift.
- Release Rust and production Rails with the same data. Rails runs without
  nginx for the HTTP rows, as on October 19; a standard install adds nginx
  compression and static serving in front.
- Bypass rows measure application work; eligible rows measure response-cache
  delivery. Browser visits were anonymous and cache-eligible.
- Non-2xx counts were checked first: all zero. Search limits were raised in both
  databases so search rows measure search, not HTTP 429.
- HTML over HTTP does different work on each side. The browser table is the
  page-load comparison.
- Local test: client, servers and PostgreSQL on one shared machine, keep-alive
  disabled, five-second samples. The applications have different process and
  concurrency models. No logged-in or mixed traffic.

## Reproducing

```bash
nix-shell
scripts/bench-corpus scripts/fixtures/public-meta-clean-bench.json \
  bench/20261024-release/http \
  rs=http://127.0.0.1:8091 rails=http://127.0.0.1:3046
scripts/bench-browser --rust http://127.0.0.1:8091 \
  --rails http://127.0.0.1:3046 --out bench/20261024-release/browser
```

Defaults are five seconds, concurrency 16 and three rounds. Restore the cleaned
snapshot into both databases, analyze, verify both connections, and restart
both servers with an empty, isolated Rails Redis database first. For the
browser run, Rails needs `DISCOURSE_SERVE_STATIC_ASSETS=true` when no nginx is
in front. The per-round results are in
[benchmarks/20261024-release-http.tsv](benchmarks/20261024-release-http.tsv).
